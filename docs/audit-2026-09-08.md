## Bug reportado: lag al panear/zoom → menús flotantes desaparecen o se parten

**No es un bug de Preact.** Tres causas, todas corregidas y documentadas en spec 04:

1. **Re-render del árbol completo por frame.** `App` seleccionaba `s.viewport`; `setViewport`
   creaba un objeto nuevo por llamada; `panBy` lo llama en cada `pointermove`. Cada píxel de pan
   re-renderizaba tablas visibles, `EdgeLayer` (vnode tree SVG completo), menús flotantes y
   modales cerradas. Además `zoomButtons.tsx` tenía un selector que devolvía un objeto nuevo
   (re-render en **toda** mutación del store). → Cámara fuera de Preact (transform imperativo),
   `useVisibleNames` con `Set` estable, identity guard en `setViewport`, `memo()` en 13
   componentes, listeners del canvas ya no se re-atan por cambio de índice espacial.
2. **Una capa GPU por tabla.** `translate3d` en cada nodo dentro de `.ddd-world { will-change }`
   → cientos de layers compositados re-rasterizados en cada paso de zoom; al agotar el presupuesto
   de tiles Chromium evicta capas de todo el proceso (el chrome fuera del canvas "se parte").
   → `translate` 2D en todos los nodos; sólo `.ddd-world` promovido. **Hipótesis fuerte no
   confirmable estáticamente: hay que medir** (ver "Verificación manual").
3. **Sin error boundary.** Un throw en `EdgeLayer`/`TableNode` abortaba el commit de Preact antes
   de diffear el chrome (hermano posterior) → menús a medio pintar sin diagnóstico.
   → 3 `ErrorBoundary` (canvas / toolbars / overlays) con `error:log` al host y "Retry".

## 2. Confirmed findings by area

### Layout / A*

**`src/webview/layout/edgeOrder/astar.ts:157` — searchGrid allocates ~400 MB of typed arrays per edge, uncapped by MAX_EXPLORED** *(high)*

`searchGrid` (astar.ts:153-166) eagerly allocates four typed arrays sized `N*5` (`N = grid.cols*grid.rows`) — `Float64Array g .fill(Infinity)`, `Int32Array cameFrom .fill(-1)`, `Uint8Array closed`, `Float64Array fOf` — before the first heap pop at astar.ts:203. The only gate is `MAX_GRID_CELLS = 4_000_000` (constants.ts:25) checked in `buildRouteGrid` (grid.ts:189); `orderEdges` builds the window as `inflate(union(sourceTable,targetTable), GRID_MARGIN)` (astar.ts:334-346) with no further size filter, and `computeEdgeOrdering` (smartLayout/edgeOrdering.ts:130) forwards every non-manual ref. Because the search closes at most `MAX_EXPLORED = 6000` nodes (constants.ts:37), over 99.9 % of those slots are never read — the explored-node cap cannot bound the allocation. Sizing for the `ordinal*5+dir` node id is correct; the defect is eagerness. Peak residency is one edge's arrays plus GC lag (each call's arrays are unreachable on return), so the batch effect is GC churn plus repeated O(N) fill work, not cumulative growth. Measured: 3.84 M cells = 385 MB and ~95 ms of pure allocate+fill per edge before any A* step; 1.4 M cells = 140 MB / 39 ms. The batch loop's only yield is `await Promise.resolve()` (astar.ts:355), a microtask that never returns to the event loop, so the webview cannot paint — a hard freeze with the progress bar stuck. If the allocation throws under memory pressure, the bare `catch` in smartLayout/runner.ts:121 (arrange) and :165 (order-edges-only) swallows the `RangeError` and the operation applies nothing, table positions included, with no error surfaced.

*Trigger:* Table A at (0,0), table B at (46000,46000) — reachable by repeated drags at `zoomMin` 0.08 (~12.5 world units/px, shared/types.ts:262; positions are never clamped, store.ts:304-316) or deterministically via a hand-edited/merged `.dbml.layout.json`, which accepts any finite coordinate (layoutStore.ts:132, `numeric()` :154-159). Then run "Order edges" or auto-arrange with edge ordering on: `inflate(union(A,B),128)` → 1939×1938 = 3.76 M cells, just under the 4 M ceiling, so `buildRouteGrid` returns a grid instead of the H-V-H fallback and `routeOneEdge` (astar.ts:277) calls `searchGrid` unconditionally. Plain dagre auto-arrange alone does **not** reach this (~300 tables ≈ 69 k cells / ~7 MB per long edge); an outlier position is required.

*Fix (one line):* lower `MAX_GRID_CELLS` in edgeOrder/constants.ts:25 from `4_000_000` to ~`250_000` (caps eager arrays at ~26 MB/edge; larger windows take the existing H-V-H fallback) — the correct structural fix is making `g`/`cameFrom`/`fOf`/`closed` sparse (Map/Set keyed by node id) so allocation scales with `MAX_EXPLORED`, not `N*5`.

**`src/webview/layout/edgeOrder/astar.ts:254` — routeOneEdge docstring claims a two-candidate lowest-cost side comparison that does not exist** *(low, spec-drift)*

The docstring at astar.ts:254-257 states the router picks "the lower-cost of two candidate side-pairs (the given Phase-1 sides, plus a 4-side `chooseSides` that may pick top/bottom)". The body (astar.ts:259-316) makes exactly one `searchGrid` call (line 279) using the caller-supplied `ep.sourceSide`/`ep.targetSide`, and `search.cost` (produced astar.ts:251, typed astar.ts:140) is never read — `RoutedEdge` (astar.ts:43-53) has no cost field. `orderEdges` calls `routeOneEdge` once per edge (astar.ts:347). The only cost-free side pick is `chooseSides4` at edgeOrdering.ts:87, one unconditional provisional pair per ref before `routeRefs`/`orderEdges`; it is not a caller of `routeOneEdge`.

*Trigger:* No runtime failure. A maintainer reading the docstring believes cost-based 2-way/4-way per-edge side selection already exists, and either skips implementing spec 05 §9 goal 3 ("mejor selección de lado") or misdiagnoses a reported bad side choice as already-optimal when no cost was ever computed.

*Fix (one line):* rewrite the docstring to "routes between the given Phase-1 sides" — code change not required.

### Host (extension)

**`src/extension/layoutStore.ts:71` — corrupted (non-conflict) sidecar JSON is silently wiped to an empty layout** *(medium)*

`readLayout` (layoutStore.ts:44-57) throws `LayoutConflictError` only when conflict markers are present; every other malformed input falls through to `parseLayout`, which returns `emptyLayout()` on any `JSON.parse` throw or non-object root (layoutStore.ts:71-78). `loadSharedLayout` (panel.ts:414-416) then adopts that empty layout as `this.currentLayout` with no warning — unlike the conflict path, which warns and attempts recovery. The next persist (drag, color, zoom → `flushPersist` → `writeSharedLayout`) overwrites the sidecar with the empty-derived layout. The defect is the missing warning plus the `emptyLayout()` fallback, not `parseLayout` itself, whose lenient behavior is required by mergeResolver.ts:36-38 and panel.ts:670/703. Impact is recoverable (atomic writes leave the corrupt file intact until the next mutation; the sidecar is git-tracked) and visible, hence medium.

*Trigger:* User hand-edits `schema.dbml.layout.json` — explicitly encouraged by spec 03 as git-diff-reviewable — and leaves a trailing comma or unbalanced brace. On the next panel hydrate/reload the diagram visibly resets to defaults with zero warning; the first subsequent drag persists the empty layout, destroying all saved positions, colors and edge routing.

*Fix (one line):* have `readLayout` throw a distinct `LayoutParseError` on `JSON.parse` failure and have `loadSharedLayout` warn and return `this.currentLayout` instead of `emptyLayout()`.

**`src/extension/panel.ts:667` — time-travel silently pairs a historic layout with the CURRENT (wrong) schema on parse failure** *(low)*

`enterTimeTravel` (panel.ts:663-673) does `const schema = parsed.error ? this.lastValidSchema : parsed.schema` and posts `git:timeTravel:enter` with today's schema under the old revision's label and the old revision's saved positions. The `git:timeTravel:enter` payload (shared/types.ts:303) has no error field, so the webview cannot detect the substitution. This is inconsistent with the codebase's own convention: `sendSchema` (panel.ts:361-366) also falls back to `lastValidSchema` but ships `parseError: result.error` so the banner shows; `enterDiff` (panel.ts:695) takes the conservative route of an empty base schema. Only the time-travel path both substitutes present-day data and drops the error.

*Trigger:* Any committed revision whose `.dbml` does not parse — a WIP commit, a commit made outside the extension, a merge commit carrying conflict markers, or syntax the current bundled `@dbml/core` parser rejects. `enterTimeTravel` is reachable from any row in the History pane (gitPanel.tsx:273 → panel.ts:216) and `gitLog` does no parseability filtering. The overlay renders labeled as the old revision but with today's table/column set at the old commit's positions: tables that did not exist then appear at defaults, genuinely-historic tables/columns are invisible, no indication is given.

*Fix (one line):* add a `parseError` field to `git:timeTravel:enter` (types.ts:303) and send an empty schema, or refuse to enter and warn like the `dbmlSrc == null` branch at panel.ts:661-664.

**`src/extension/panel.ts:694` — enterDiff() treats a HEAD parse failure as an empty base schema, producing a false "everything added" diff** *(low)*

`enterDiff` (panel.ts:692-696) substitutes `{ tables: [], refs: [], groups: [] }` when HEAD's committed `.dbml` fails to parse, so `diffSchemas` (schemaDiff.ts:12-33) reports every current table and ref as `added` with no removed/modified entries. The `git:diff:enter` payload (shared/types.ts:305) carries no error field for the webview to detect it, and no warning is shown — in direct contrast with the `baseDbml == null` branch two lines above, which does warn and abort. Reachable in-product because commit is not gated on parse validity (panel.ts:534-556, gitPanel.tsx:177). Read-only overlay, no writes, recoverable by exiting diff, and it needs an unparseable HEAD blob — hence low, not medium.

*Trigger:* HEAD's committed `.dbml` fails to parse with the current parser (stale commit predating a syntax change, or a bad merge left invalid DBML at HEAD). The user sees the entire schema highlighted as newly added versus HEAD, silently.

*Fix (one line):* mirror the `baseDbml == null` branch — warn and abort (or add an error field to the payload) instead of falling through, and reconcile with `enterTimeTravel`'s divergent fallback at panel.ts:668.

### Export (TypeORM exporter)

**`src/extension/exporters/typeorm/relations.ts:158` — relation-name collision suffix isn't propagated to the sibling side's inverse callback** *(medium)*

`propNameFor` derives every decorator's property name from the *table* only (relations.ts:110-111), not the FK column or `ref.name`, so two FKs between the same pair of tables produce identical names on **both** endpoints. `inversePropertyName` is captured at pair-construction time (relations.ts:113-137), before any collision resolution. `relationsByOwner` (relations.ts:158-167) later de-duplicates by renaming `propertyName` only (`candidate` → `orders_2`), leaving every already-captured `inversePropertyName` — including the sibling pair's copy — untouched. The generated code still type-checks, which is what makes it silently wrong: TypeORM resolves inverses by property name, so the likely outcome is duplicated/incorrect wiring (both collections mapped through the same owning property) rather than a guaranteed metadata build throw.

*Trigger:* `Ref: orders.created_by > users.id` and `Ref: orders.updated_by > users.id`. Both are many-to-one from orders, so both pairs compute the same OneToMany name `orders` on User; the second is renamed to `orders_2`, but its Order-side `@ManyToOne` was built with `inversePropertyName: 'orders'` and is never updated. `emitRelation` (template.ts) emits `@ManyToOne(() => User, (user) => user.orders)` on **both** `created_by` and `updated_by`, while `User.orders_2` has no owning-side back-reference. Symmetrically, Order gets `user` and `user_2`, both emitting `(user) => user.orders`. Fires on every export of a schema with more than one FK between the same pair of tables.

*Fix (one line):* back-patch the sibling pair's `inversePropertyName` when `relationsByOwner` renames a `propertyName` (or resolve collisions during pair construction, keying the name on the FK column / `ref.name` when the table-derived name is taken).

### Render hot path

**`src/webview/drag/dragController.ts:145` — edge waypoint/notch/slide/endpoint drag re-routes ALL refs on every pointermove** *(low)*

`setEdgeWaypoints` / `setEdgeSide` (store.ts:358-366, 387-400) always return a fresh `edgeLayouts` Map with no value-equality bail-out, so the `edgeLayouts` dependency at edgeLayer.tsx:104-106 invalidates the global route memo once per pointermove and `routeRefs` recomputes geometry for every ref in the schema. This is the same documented O(refs)-per-movement design as the table-drag path (spec 05 §8.1, "O(refs) una vez por movimiento") reached through a different dependency, and it costs strictly less per frame than a table drag (no spatial-index rebuild, no cull re-query, no `TableNode` re-render). The genuinely avoidable waste is `startEndpointDrag` (dragController.ts:266-270) writing `setEdgeSide` on every pointermove even when the resolved side is unchanged — a two-valued quantity that flips a handful of times per drag.

*Trigger:* In a diagram with thousands of refs, drag one edge's midpoint (slide) or notch handle, or flip an endpoint's port side. Each of the ~60-120 pointermove events re-routes every ref in the schema, dropping frames in proportion to total ref count while editing a single edge.

*Fix (one line):* add an equality short-circuit in `setEdgeSide`/`setEdgeWaypoints` (mirroring `resetEdgeShape`'s `return s`) so an unchanged side or waypoint list does not allocate a new Map.

### UI

**`src/webview/render/tableNode.tsx:60` — buildDiffRows can emit a removed column twice when columns are reordered** *(low)*

`flushRemovedBefore` (tableNode.tsx:50-56) advances a shared cursor `bi`, but line 60 resets it with `bi = base.indexOf(bc) + 1`, which can rewind `bi` behind ground already scanned. The final `flushRemovedBefore(base.length)` then re-scans that range and re-emits any base column still absent from `curByName`. The trigger is narrower than "columns reordered": it needs a *backward-crossing* reorder (a kept column whose base index is below one `bi` already passed) **and** a genuinely-removed base column inside the re-scanned range — a pure reorder never even marks a table `modified`, since `diffColumns` compares by name only (schemaDiff.ts:52-65). Exhaustive simulation over base `[A,B,C,D]` with all subsets/permutations of kept columns: 5 of 51 cases duplicate. Impact is cosmetic and confined to the read-only git-diff overlay — one extra `removed` ghost `<li>` and duplicate Preact keys in the same `<ul>` (tableNode.tsx:204); no column is ever omitted, and the underlying `ColumnDiffEntry` data is order-insensitive and correct.

*Trigger:* base `[A,B,C]` with B removed, current `[C,A]` (C and A kept but reordered ahead of B's slot, e.g. the user reordered columns in the `.dbml` between the two revisions being diffed). `cc=C` flushes removed-B and sets `bi=3`; `cc=A` rewinds `bi` to 1; the terminal flush re-scans index 1 and pushes removed-B a second time, yielding two rows keyed `-B`.

*Fix (one line):* track already-flushed base indices in a `Set` (or never rewind `bi`) so each removed base column can be emitted at most once.

**`src/webview/render/gitPanel.tsx:141` — commit message is discarded optimistically before the host confirms success** *(low)*

`commit()` (gitPanel.tsx:137-142) calls `setMessage('')` synchronously right after posting `git:commit`, before any host result arrives. `message` is component-local `useState` in `CommitPane`, and main.tsx:79-81 handles `git:commitResult` by only calling `setGitBusy(false)` — it never routes `ok`/`message` back to the pane, so nothing can restore the text. The failure itself is not silent (panel.ts:556-557 posts `git:commitResult{ok:false, message}` and fires `showErrorMessage`), and the field is a single-line `<input type="text">` (gitPanel.tsx:158-166), so what is lost is one subject line, not a long message.

*Trigger:* User types a commit message and clicks Commit in a repo with no configured `user.name`/`user.email`, or with a pre-commit hook that rejects. `gitCommit()` throws in gitStages.ts; the error toast appears but the input is already cleared and the text must be retyped.

*Fix (one line):* move `setMessage('')` out of `commit()` and clear it only on an `ok:true` `git:commitResult` (via a store-held pending message or an ok/nonce flag).

**`src/webview/ui/Slider.tsx:26` — live readout never resyncs when `value` changes externally, despite a comment claiming it does** *(low)*

`const [live, setLive] = useState(value)` seeds only at mount, and the adjacent comment ("Keep the readout in sync when the committed value changes from outside (e.g. reset to default)") describes a `useEffect` keyed off `value` that does not exist anywhere in the file. The thumb position and numeric readout therefore keep showing the pre-change value until the user physically drags the slider. The stale state is **not** cleared by closing and reopening the Settings modal (Modal.tsx keeps children mounted), but it is cleared by switching settings category tabs and back, since settingsPanel.tsx conditionally renders each Section.

*Trigger:* Open Settings and click "reset to defaults", or change `AppSettings.ui.layoutSpacing` from any external path (editing `settings.json` — the host echoes `settings:loaded` on every config change). settingsPanel.tsx passes the new `value`, the slider keeps rendering the old number, and the UI visibly disagrees with the committed setting.

*Fix (one line):* add `useEffect(() => setLive(value), [value])` in Slider.tsx.

## 4. Refuted

- **`src/extension/mergeResolver.ts:36` — Transient git-read failure during merge silently treated as an empty stage.** `git show :2:<path>` is a read-only index/object-DB read: `.git/index.lock` never blocks readers and `git repack` writes the pack before pruning loose objects, so both cited triggers are non-mechanisms; the immediately preceding `git ls-files -u` in the same repoRoot already proved the environment works, and `maxBuffer` is 64 MB. The silent-empty path is the module-wide contract anyway (`parseLayout` returns `emptyLayout()` on any parse failure), and `handleConflict` writes nothing on the conflict path — the zero-conflict auto-write branch is unreachable here. Residual (`stages.has(N) ? … ?? ''` cannot distinguish read-failure from empty blob) is a theoretical robustness gap, not high severity.
- **`src/webview/app.tsx:607` — MergeGhosts and DiffGhosts render every ghost unconditionally, no viewport culling.** The code reading is true but the sizing is not: `enterDiff` (store.ts:557-563) creates a ghost only for `status === 'removed'` tables with a saved position — added/changed/moved tables go through the culled `TableNode` path — and `mergeThreeWay.ts:67-75` emits a conflict only when both sides changed the same key differently, so a large one-sided rebase produces zero ghosts. app.tsx:570 also suppresses the live node for each conflicting table, and specs/14 and /16 scope the culling guarantee to live tables, explicitly specifying removed tables as uncalled ghosts.
- **`src/webview/layout/smartLayout/runner.ts:123` — Stale run's abort-cleanup clobbers a newer run's progress/cancel state.** The race needs two concurrent runs, which the event loop forbids: astar.ts:354 yields with `await Promise.resolve()` (a microtask), and there is no `setTimeout`/rAF/rIC/worker anywhere in astar.ts, grid.ts or edgeOrdering.ts, so the whole run from `beginProgress()` through the catch/success path executes in one uninterrupted task — no click or host postMessage can start run B meanwhile. Both paths null `activeArrange` (runner.ts:126 and :130), so isolating the catch block also misreads the code shape. (The same evidence does expose a different, unclaimed defect: the progress overlay never repaints, so its Cancel button can never be clicked mid-run.)
- **`src/webview/render/mergeGhosts.tsx:18` — MergeGhosts re-renders its entire un-memoized ghost list on every hover transition.** The hover subscription is not the cause: `App` subscribes to `viewport` (app.tsx:45) and renders `<MergeGhosts />` inline (app.tsx:607), so the full list is already re-mapped on every pan/zoom frame — a path spec 14 explicitly sanctions during merge — dominating discrete pointerenter/leave by two orders of magnitude. The implied `memo()` fix would miss every comparison because `Ghost` gets fresh `onHover`/`onPick` closures per render, and no component in src/webview uses `memo()`. specs/14 records the measured real case as 2 conflicts out of ~113 tables.
- **`src/webview/render/edgeRouter.ts:213` — Zero-length rigid stubs collapse the editable middle into a false "rigid" segment.** The arithmetic is right, the framing is not: the MIN_STUB doc block at edgeRouter.ts:8-13 documents "a very-close same-row edge then has no editable middle" as the deliberate tradeoff over crossing stubs, and `roundedPathString` (edgeRouter.ts:277-278) already drops coincident points. Table coordinates are integers (layout/grid.ts:9), so `stubLen === 0` needs the facing edges within 1 unit — a two-position window pinned by edgeRouter.stub.test.ts. Endpoint handles and the Reset-line toolbar stay available (edgeLayer.tsx:383-391). Residual is a stale comment at edgeRouter.ts:348-349 plus stale spec 05:484-486 text.
- **`src/webview/state/store.ts:549` — enterTimeTravel/enterDiff don't clear mergeConflicts, breaking documented mutual exclusion.** Unreachable: both producers are double-guarded in the webview (gitPanel.tsx:263/:335 render "Resolve the active merge…" instead of the buttons, and the handlers early-return at :273/:340), and the host emits `git:timeTravel:enter`/`git:diff:enter` only in reaction to those messages. Only a sub-frame race co-exists. Impact is also inflated: `isCanvasReadOnly` is an OR so edits stay blocked, and MergePanel's Apply has no gitView gate, so the merge never gets stuck.
