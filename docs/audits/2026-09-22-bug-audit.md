## HIGH

### F01 · Sidecar echo guard compares against the last self-write, so an external revert back to that content is ignored and the next edit overwrites it with a stale layout
- **Status:** CONFIRMED · orig critical · data-loss · areas: protocol-contract, persistence, git-merge-host
- **Location:** `src/extension/panel.ts:839` · related: `src/extension/panel.ts:843`, `src/extension/panel.ts:426`, `src/extension/panel.ts:627`, `src/extension/panel.ts:795`, `src/extension/layoutStore.ts:42`
- **Failure:** On main, drag a table (the extension writes X), then commit. `git checkout feat` in the terminal loads Y. `git checkout main` restores X, which equals lastWrittenSerialized, so the event is ignored and the panel still shows Y. Drag any table and Y plus the drag is written into main's sidecar. `git stash` / `git stash pop` loses the popped layout work the same way. Reproduced with a vscode-mock harness: 0 layout messages after switching back, and the disk ended up with the other branch's value (a.x=999 / x=555).
- **Fix:** Track the last known disk content rather than the last write. When onLayoutFs reloads (text differs), set `lastWrittenSerialized = text` (or null) before calling sendLayout(true). Alternatively, record the raw text inside loadSharedLayout on every successful external read (hydrate, reloadFromDisk).
- **Verifier notes:** The suggested direction is right: track the last known disk content, not the last self-write. Two refinements.

1. Do not set the guard from the `text` read in onLayoutFs. sendLayout re-reads the file, and the two reads can differ. Have readLayout/loadSharedLayout return, or record, the raw text it actually adopted. Record it on every read: hydrate, the watcher path and reloadFromDisk.

2. Do not use null as the steady-state value. With null, flushPersist's `sharedSerialized !== this.lastWrittenSerialized` is always true, so the first view-state-only persist rewrites the sidecar. If the disk copy is non-canonical (hand-edited or produced by a merge), that creates a spurious git diff. Storing the raw disk text keeps the dedup meaningful and still lets the first real edit write canonical output.

Also record the text on the conflict and parse-error branches, i.e. the conflicted or corrupt text. Then a later `git merge --abort` back to the previous self-write no longer matches the guard, which covers F03.

On severity: I lowered it from critical to high. Only layout positions and colours are lost, never the .dbml schema. In the branch case the overwritten content is still in the commit and shows as a dirty sidecar. The git paths do not reproduce under Windows' default autocrlf=true. The stash-pop path ("stash, pull, pop") does lose uncommitted work silently, which is why it stays high rather than medium.

### F02 · Webview reload (hide/show) during a pending merge never re-posts merge:begin, so the canvas becomes editable and the next edit overwrites the conflicted sidecar with the provisional 'ours' merge
- **Status:** CONFIRMED · orig high · data-loss · areas: host-lifecycle, protocol-contract, persistence, git-merge-host, git-merge-webview
- **Location:** `src/extension/panel.ts:512` · related: `src/extension/panel.ts:87`, `src/extension/panel.ts:366`, `src/extension/panel.ts:371`, `src/extension/panel.ts:774`, `src/extension/panel.ts:787`, `src/webview/state/store.ts:226`, `src/webview/persistence.ts:19`
- **Failure:** The sidecar conflicts after a pull and the resolver opens. The user clicks another tab in the same group and comes back. The merge bar is gone. The user drags a table, and about 500 ms later the sidecar has no markers and keeps a.x=111 (ours; theirs was 222) while `git status` shows `UU`. Reproduced: the first hydrate posted 1 merge:begin and the second posted 0.
- **Fix:** Reset `this.lastPostedMergeSig = null` at the start of hydrate(), because every `ready` comes from a fresh webview with no merge state. As defense in depth, make onLayoutPersist/flushPersist (and resetLayout/pruneOrphans) refuse the shared write while `this.pendingMerge` is set.
- **Verifier notes:** The primary fix is right: set `this.lastPostedMergeSig = null` as the first line of `hydrate()`, before `sendLayout()`. Every `ready` comes from a webview document with an empty store, so no conflict set is "already on screen". Resetting it to null, rather than just forcing a post, also avoids the misleading "layout changed on disk — the conflict list was refreshed" warning at panel.ts:513-514.

For defense in depth, put the guard inside `flushPersist` itself: `if (this.sidecarCorrupt || this.pendingMerge) { /* skip shared write */ }`, and keep writing view-state. One guard there covers onLayoutPersist, plus `resetLayout()` and `pruneOrphans()`. Those two are host-side command paths that bypass the webview's `isCanvasReadOnly` and would otherwise also clobber a conflicted sidecar during a merge. `resolveMerge` writes through `writeSharedLayout` directly, not through flushPersist, so the guard does not block Apply.

Consider a regression test built like this harness: two `ready` messages while a merge is pending should post `merge:begin` twice.

### F05 · Time travel → 'Diff against HEAD' → Exit leaves the past revision on an editable canvas, and the next edit persists the old commit's layout over the working sidecar
- **Status:** CONFIRMED · orig high · data-loss · areas: protocol-contract, git-merge-webview
- **Location:** `src/webview/render/gitPanel.tsx:344` · related: `src/webview/render/gitBanner.tsx:77`, `src/webview/state/store.ts:508`, `src/webview/state/store.ts:569`, `src/webview/state/store.ts:606`, `src/webview/persistence.ts:19`, `src/extension/panel.ts:734`, `src/extension/layoutStore.ts:46`
- **Failure:** Git → History → pick an old commit. Git → Diff → 'Diff against HEAD'. Exit the diff banner. The canvas is editable and shows the old tables. The user drags one table and the working sidecar is overwritten with the old commit's positions, so tables added since then lose their positions. Reproduced with a store harness: readOnly=false, and the persist payload held only the past positions.
- **Fix:** Block Diff (and the Stash/Discard panes) while gitView.kind === 'timeTravel', or exit time travel through the host and wait for layout:loaded before entering the diff. When the store is not showing working state, make the diff Exit ask the host to re-send it. When beginMerge replaces a timeTravel view, request the working schema.
- **Verifier notes:** 1. **Minimal fix.** Gate DiffPane on any active git overlay, not only on a merge: `const blocked = useAppStore((s) => s.mergeConflicts != null || s.gitView?.kind === 'timeTravel')`. Use it both in `showDiff` and in the rendered pane (show a notice such as "Exit the earlier version before diffing").
2. **Defensive check for the async reply.** Also guard main.tsx's `git:diff:enter` case: ignore the message when `store.getState().gitView?.kind === 'timeTravel'`. The host reply can arrive after the state has changed.
3. **More robust host-side option.** Have the host track `timeTravelActive` (set in `enterTimeTravel`, cleared in `exitTimeTravel`). `enterDiff` should then either refuse, or run `exitTimeTravel()` first (which re-sends the working schema and layout) before posting `git:diff:enter`.
4. **Scope corrections to the suggested fix:**
   - The beginMerge sub-claim does not need a schema re-request to prevent data loss. The watcher path already posts `layout:external-change` with the working layout before `merge:begin`, so only the displayed schema is stale.
   - Stash/Discard during time travel reload the working schema and layout under a mislabeled time-travel banner. The canvas stays read-only, so that is a cosmetic fix: gate those panes on time travel too, or have `reloadFromDisk` post `git:timeTravel:exit` first.
   - The F29 exit-ordering window is a separate issue.

### F06 · Stale-closure auto-layout effect overwrites freshly loaded table positions after time-travel exit or a stash/restore reload
- **Status:** CONFIRMED · orig high · race-condition · areas: render-pipeline
- **Location:** `src/webview/app.tsx:95` · related: `src/extension/panel.ts:734`, `src/extension/panel.ts:626`, `src/webview/state/store.ts:315`, `src/webview/main.tsx:20`
- **Failure:** The working diagram has orders_v2, added after commit X and with a saved position. The user time-travels to X and exits. schema:update (which includes orders_v2) is followed about 2-10 ms later by layout:loaded. The stale effect places orders_v2 near (32,32) on top of other tables. The next drag persists that position and the real one is lost. Reproduced in Node with preact/hooks and zustand.
- **Fix:** Inside the effect, derive `missing` from store.getState() (current schema and positions), and skip when `store.getState().positions !== positions`. Also send the layout before the schema in exitTimeTravel/reloadFromDisk, as hydrate does.
- **Verifier notes:** Use the effect-side fix. Sending the layout before the schema in exitTimeTravel/reloadFromDisk is not enough by itself. With layout first, the pending effect would flush with the OLD (past) schema and the NEW positions. It would then lay out past-only tables (tables deleted since that commit) and merge orphan positions into the working layout, and those would get persisted.

Recommended fix: in app.tsx:95-105, read `const { schema, positions } = store.getState()` inside the effect, or compute `missing` from that state. Keep the closure deps only as re-run triggers. A late flush then sees the positions that were just loaded and does nothing, so no ordering between messages can clobber state.

The alternative guard `if (store.getState().positions !== positions || store.getState().schema !== schema) return;` also works: the fresh effect queued by the newer render handles any real missing tables.

Optionally also send the layout first in exitTimeTravel, for symmetry with hydrate, but only together with the effect fix.

On the reloadFromDisk path the sidecar watcher usually repairs the store (lastWrittenSerialized is nulled), so that path is intermittent. The effect fix covers it too.

### F07 · Edge-ordering, arrange reset and selection reset key EdgeLayouts by the parser Ref.id, but the renderer and every edge edit key them by a different composite id
- **Status:** CONFIRMED · orig high · correctness · areas: edge-routing
- **Location:** `src/webview/layout/smartLayout/edgeOrdering.ts:76` · related: `src/webview/app.tsx:203`, `src/webview/render/edgeLayer.tsx:108`, `src/webview/layout/smartLayout/edgeReset.ts:47`, `src/extension/parser.ts:195`
- **Failure:** 'Order edges only' or Auto-arrange with ordering: nothing visibly changes, and each ref gets an unused `A(c)->B(c)` entry in the git-tracked sidecar. Auto-arrange that moves both endpoints of a bent edge leaves stranded absolute waypoints drawing spikes. 'Reset relations (0)' is disabled even when the selected tables' edges have manual shapes. Confirmed with the real parser.
- **Fix:** Use a single shared edgeKey(ref) function in app.tsx, the smartLayout adapter, edgeReset and the runner, skipping hidden or collapsed endpoints the same way effectiveRefs does. Alternatively, key by the stable id everywhere and translate in EdgeLayer. Add a migration that drops or rekeys orphan entries. Build test fixtures with parseDbml.
- **Verifier notes:** The direction is right, with four corrections.

1. **Keep the composite key and do not rekey to stableRefId.** The composite key is what existing git-tracked sidecars already hold (see the fixtures and anything users have edited). Switching to stableRefId would orphan every user edit unless a migration runs. Extract a pure `edgeKeyFor(ref, srcMapped, tgtMapped)` helper from app.tsx into a shared module. In the runner, map s.schema.refs to that key before calling computeEdgeOrdering, computeEdgeResets and computeSelectionEdgeResets.
   - Skip any ref whose endpoint is hidden or collapsed; effectiveRefs remaps those to a group id or drops them, and A* in edgeOrdering.ts builds bboxes from raw table positions only.
   - Dedupe the same way the `seen` set in app.tsx:209 does, so two parallel refs that share a composite key do not produce two SET pairs for one key.
2. **Drop existing orphans on load.** Earlier runs have already persisted orphan `A(cols)->B(cols)` keys. Add a one-time prune in setLayout or persist that removes keys matching the stableRefId shape (containing '->' and no '::'). Do not rekey them: the A* output they hold is stale.
3. **Rebuild the tests on the real parser.** Build edgeOrdering.test.ts and edgeReset.test.ts fixtures with parseDbml plus the shared key helper. Assert that EdgeLayer's lookup, meaning routeRefs over effectiveRefs, sees the result.
4. **The composite key has its own weakness.** Unlike stableRefId it is not order-normalized or column-sorted. Worse, when an endpoint is collapsed it becomes `group:...::col`, so an edit made while a group is collapsed is keyed differently from the same edge expanded. That should be tracked separately so the fix does not bake it in. The F42, F43, F18 and F75 routing defects will surface once this is fixed, as the finding says.

### F03 · Conflict resolved or aborted outside the diagram leaves the webview stuck in merge mode, with Apply hanging on 'Applying…' (or Apply staging the aborted merge)
- **Status:** CONFIRMED · orig high · correctness · areas: host-lifecycle, protocol-contract, git-merge-host, git-merge-webview
- **Location:** `src/extension/panel.ts:509` · related: `src/extension/panel.ts:454`, `src/extension/panel.ts:492-500`, `src/extension/panel.ts:523`, `src/extension/panel.ts:626`, `src/extension/panel.ts:839`, `src/webview/main.tsx:73`, `src/webview/render/mergePanel.tsx:45`, `src/webview/render/gitPanel.tsx:151`
- **Failure:** (a) The resolver is open and the user runs `git checkout --theirs` + `git add`, or `merge --abort`. The host posts only layout:external-change and git:status. Clicking Apply posts nothing, and the canvas stays read-only until the panel is reopened. (b) The last local layout write came from the panel before the pull. `git merge --abort` restores the same bytes and the watcher ignores it. Apply writes the aborted branch's value (a.x=222 / public.b.x=700), and git status shows `M  s.dbml.layout.json` staged. Both cases were reproduced with a harness and a real repo.
- **Fix:** In maybePostMerge, when pendingMerge is null and lastPostedMergeSig !== null, post `{type:'merge:done'}` before clearing the signature. In resolveMerge, when pending is null, post merge:done (plus a warning) instead of returning silently. Do not take the echo early-return in onLayoutFs while pendingMerge is set. Gate the Git panel's Discard/Stash actions during a merge.
- **Verifier notes:** The suggested fix is correct, with these refinements:

1. **In `maybePostMerge`:** when `pendingMerge` is null and `lastPostedMergeSig !== null`, post `{type:'merge:done'}` before clearing the signature. A fresh webview (after hydrate) may receive `merge:done` while not in merge mode. That is harmless, because `endMerge` is idempotent.

2. **In `resolveMerge`:** when `pending` is null (and `mergeResolving` is not already set), post `merge:done`, and optionally a "conflict already resolved on disk" info message, instead of returning silently.

3. **For the abort/echo case, reset `lastWrittenSerialized = null` inside `handleConflict`** when it stores a non-empty `pendingMerge`. The file on disk now holds markers and no longer matches any write of ours, so the next disk change must be re-read. This is simpler and more local than special-casing the early return in `onLayoutFs`.

4. **Gating Discard/Stash in CommitPane/StashPane is optional** once items 1 and 2 are in place. With them, Discard during a merge becomes "resolve to HEAD" and exits merge mode correctly. Gating it (as HistoryPane and DiffPane already do) is still reasonable UX.

**Severity:** lowered to medium. With `retainContextWhenHidden:false`, hiding and re-showing the panel clears the stuck state. The staged content in case (b) can be undone through git, and it only happens after the user explicitly clicks Apply in the stale UI.

### F04 · When conflict detection fails, the empty/stale layout stays writable and the first edit overwrites the conflict-marked sidecar
- **Status:** CONFIRMED · orig high · data-loss · areas: host-lifecycle, protocol-contract, git-merge-host
- **Location:** `src/extension/panel.ts:485` · related: `src/extension/mergeResolver.ts:34`, `src/extension/panel.ts:461-466`, `src/extension/panel.ts:793`
- **Failure:** After a conflicted merge the user runs `git add -A` (or a teammate commits the markers), then opens the diagram. The warning appears and layout:loaded has `tables: {}`. The user drags one table and the sidecar becomes plain auto-layout JSON, with both branches' positions gone. Reproduced with the harness, including through a symlinked path.
- **Fix:** In the handleConflict catch branch, set `this.sidecarCorrupt = true` (or a dedicated sidecarUnresolved flag that flushPersist checks), so shared writes are refused until loadSharedLayout reads a clean file.
- **Verifier notes:** The suggested fix is correct: set `this.sidecarCorrupt = true` in the `handleConflict` catch at panel.ts:485. The existing mechanics already cover the rest. `loadSharedLayout` clears the flag on a clean read (panel.ts:454). After a manual fix, the watcher re-reads the file because `lastWrittenSerialized` will not match (panel.ts:835-840). The flag name is now slightly misleading, so consider renaming it to something like `sharedWritesBlocked`.

During a normal pending merge, they would write the provisional layout over the conflict-marked file. Add `|| this.pendingMerge` to the guard at panel.ts:793.
(2) The UX is the same as the parse-error path: edits in the webview are silently dropped while writes are blocked. Consider also posting a read-only signal to the webview, or saying in the warning text that layout edits will not be saved until the markers are resolved.

### F09 · Commit, Revert and Stash fail for diagram paths with spaces or non-ASCII characters because quoted porcelain paths are reused as pathspecs
- **Status:** CONFIRMED · orig high · correctness · areas: git-merge-host
- **Location:** `src/extension/gitStages.ts:114` · related: `src/extension/panel.ts:597`, `src/extension/panel.ts:643`, `src/extension/panel.ts:664`
- **Failure:** With `docs/modelo de datos.dbml` or `esquema_añadido.dbml`, clicking Commit fails with `fatal: pathspec '"my schema.dbml.layout.json"' did not match any files`. Revert and Stash fail the same way. Verified against a real repo.
- **Fix:** Use `git status --porcelain=v1 -z` and split on NUL; renames then carry the source path as a separate field. Better still, have the callers use the known, unquoted scope.relpaths filtered by status membership.
- **Verifier notes:** The core fix is right; drop the rename claim from the finding. Recommended fix: run `git status --porcelain=v1 -z` and split the output on '\0'. Each entry is `XY<space>path`, and the path is never quoted. With `-z`, a rename or copy entry (X or Y is R or C) is followed by an extra NUL-terminated field holding the original path. The parser must skip that field, or it will come out as a bogus entry. That field can't appear with today's scoped pathspec, but a robust parser should still handle it. The `-z` path strings are the same forward-slash repo-relative strings toRepoRelative produces, so the fix also cleans up the file list in the Git panel. Two weaker alternatives:
- `-c core.quotePath=false` alone does not help, because paths with spaces are still quoted.
- Having callers use scope.relpaths directly still requires matching each status entry back to a known path, which needs unquoted output anyway, so `-z` is the simpler fix.

Severity is lowered from high to medium. Every diagram path with a space or a non-ASCII character loses Commit, Revert and Stash completely, which is plausible for a Spanish-speaking audience. But the failure is loud and non-destructive: git refuses the pathspec, nothing is modified, and the user sees an error. VS Code's own Source Control view remains a workaround. Suggested regression test: a temp repo with a path containing a space and a path containing 'ñ', asserting that gitStatusPorcelain returns the raw relpaths.

### F11 · Column default kind (string/number/boolean/expression/null) is flattened to a string, so the TypeORM export emits wrong defaults
- **Status:** CONFIRMED · orig high · correctness · areas: parser, exporters
- **Location:** `src/extension/parser.ts:166` · related: `src/extension/exporters/typeorm/template.ts:130`, `src/shared/types.ts:18`
- **Failure:** `[default: `CURRENT_TIMESTAMP`]` becomes `default: "CURRENT_TIMESTAMP"`, i.e. DEFAULT 'CURRENT_TIMESTAMP', which Postgres rejects. `[default: null]` becomes `default: "null"`. `[default: '00501']` becomes `default: 501`. `[default: 'true']` on a varchar becomes `default: true`. `[default: 'now()']` becomes a SQL call. All reproduced.
- **Fix:** Add a `defaultKind` field to Column, filled from dbdefault.type, and treat the value 'null' as a null default. Have emitDefault switch on defaultKind (expression -> `() => raw`, string -> quoted literal, number, boolean, null -> omit or nullable) instead of pattern-matching the text.
- **Verifier notes:** The suggested fix is correct.

- **Parser:** in mapField, add an optional `defaultKind: 'string' | 'number' | 'boolean' | 'expression'` taken from dbdefault.type. Map {type:'boolean', value:'null'} to `default: null`. Keep the text field so the webview display does not change. The new field is optional, so it is safe across postMessage.
- **emitDefault:** switch on the kind instead of the text:
  - expression → `() => raw`
  - number → Number(value)
  - boolean → value === 'true'
  - string → string literal
  - null → omit
- **Embedded quotes:** TypeORM's Postgres normalizeDefault does not escape quotes inside a string default. A DBML value such as `'it''s'` would still produce broken DDL. Either emit `() => "'it''s'"` with the quotes doubled, or add an export warning.
- **Severity:** I rated this medium, not high. The output opens as an untitled document that the user is meant to review and edit. The most common failures (CURRENT_TIMESTAMP, int DEFAULT NULL) fail loudly at migration time. The strongest case for high is the silent varchar DEFAULT 'null' corruption, which hits every nullable varchar in MySQL-imported DBML.
- **Tests:** add a test for emitDefault covering expression, null, a numeric-looking string, and a boolean-looking string.
